01Challenge Description

챌린지 소개

대화는 그대로인데, 말한 사람이 다르게 표시된다면?

회의록에서 각 발화를 말한 사람에게 연결하는 작업을 화자 귀속 (Speaker Attribution) 이라고 합니다. 이 챌린지는 입력의 무음 길이나 등록 순서가 바뀌어도,같은 발화를 같은 사람의 말로 판단하는지 평가합니다.

이번 실험의 WeSpeaker는 회의에서 각 발화를 잘라 내고, 그 목소리를 등록 음성과 비교합니다. 대화 앞에 무음을 넣어도 잘라 낸 발화 자체는 같고, 등록 순서가 바뀌어도 비교할 목소리는 같습니다. 이 구현에서는 입력 조건이 바뀌어도 동일한 발화의 예측이 유지됩니다. 예측이 유지된다는 것은 화자를 맞혔다는 뜻과는 다릅니다. 실제 화자가 A인 발화를 B로 잘못 판단했다면, 10가지 조건에서 계속 B로 답해도 모두 오답입니다.

반면 이번 MOSS 구성은 등록 음성과 회의 음성을 이어 붙여 한 번에 입력합니다. 모델은 들은 내용을 글로 옮기는 전사(받아쓰기)와 화자 구분을 함께 수행합니다. 무음을 넣으면 발화의 입력상 위치가 바뀌고, 등록 순서를 바꾸면 모델이 먼저 듣는 목소리가 바뀝니다. 대화 속 실제 화자는 같으므로 화자 판단도 유지되어야 하는지, 이 변화를 실험으로 확인합니다.

REFERENCE

등록 음성

누구의 목소리인지 미리 알려 주는 짧은 음성입니다. 모델은 이를 기준으로 회의 속 화자를 판단합니다.

ATTRIBUTION

화자 귀속

각 발화를 등록된 사람 중 누구의 말인지 연결하는 작업입니다.

INVARIANCE

불변 정답률

정해진 10가지 입력 조건에서 모두 화자를 맞힌 발화의 비율입니다.

기존 지표는 무엇을 측정하나요?

DER(Diarization Error Rate)는 ‘누가 언제 말했는지’ 판단한 결과의 오류를 시간 기준으로 측정합니다. 말소리를 놓친 시간, 말소리가 없는데 있다고 판단한 시간, 화자를 잘못 배정한 시간을 합해 정답 발화 시간으로 나눕니다.

cpWER(화자별 단어 오류율)는 각 화자의 전사를 이어 붙인 뒤, 정답과 예측의 화자 대응을 가장 유리하게 맞춰 단어의 치환·삭제·삽입을 계산합니다. 말한 내용을 잘못 받아쓴 경우와, 말을 다른 화자에게 배정한 경우가 함께 점수에 반영됩니다.

정의: DIHARD의 DER 설명 ↗ · CHiME의 cpWER 설명 ↗

두 지표는 각 입력 조건의 예측을 정답과 비교합니다. 조건별로 반복 계산하면 전체 오류율이 얼마나 달라지는지 확인할 수 있습니다. 여기에 같은 발화의 화자 예측이 조건 사이에서 유지되는지를 직접 비교하는 절차를 추가한 것이 이번 평가입니다.

점수가 같아도, 틀린 발화는 다를 수 있습니다

아래는 발화 10개의 화자 정답 여부로 계산 방식을 설명한 예시입니다. 실제 실험 결과가 아닙니다.

계산 예시: 원본과 변형 모두 정답률은 90%지만 두 조건에서 계속 맞힌 비율은 80%
입력 조건발화 1발화 2나머지 8개정답률
원본오답정답모두 정답90%
앞 무음 추가정답오답모두 정답90%

각 조건에서는 9개를 맞혔지만, 두 조건에서 모두 맞힌 발화는 8개입니다. 이 예시의 불변 정답률은 80%가 됩니다. 따라서 조건별 점수와 함께, 어떤 발화를 계속 맞히는지도 살펴봐야 합니다.

등록 화자 ID를 기준으로 따로 채점하는 이유

화자 구분 모델의 ‘화자 1·화자 2’는 사람의 이름을 모르는 상태에서 붙인 임시 번호입니다. DER와 cpWER는 이런 번호 차이를 오류로 세지 않도록 정답·예측 화자의 대응을 맞춥니다.

이번 과제의 A–D는 미리 등록한 사람을 뜻합니다. 등록 순서를 바꿔도 A라는 사람의 정체는 같으므로, A의 발화를 계속 A로 연결하는지 채점합니다. 조건마다 A와 B를 사후에 바꿔 맞추면 등록 화자 연결의 오류를 놓칠 수 있습니다.

입력 변화의 영향을 구분하기 위해 추론 설정을 고정합니다

동일한 입력에도 실행할 때마다 출력이 달라지면, 차이가 입력 변화 때문인지 추론의 무작위성 때문인지 구분하기 어렵습니다. 그래서 이번 실험은 출력을 무작위로 뽑는 샘플링을 끄고, 매 단계 가장 높은 점수의 출력을 선택하는 greedy 설정을 사용했습니다.

기존 Starter 대조 실험에서는 동일 입력 2개를 재실행했을 때 전사와 화자·시각 출력이 일치한 것을 확인했습니다. 이 확인과 별도로 무음·등록 순서를 바꾼 조건을 실행해, 동일 발화의 예측을 비교했습니다. 설정 고정만으로 모든 입력과 실행 환경에서 동일 출력이 보장된다고 해석하지는 않습니다.

예비 실험에서 확인한 차이

앞 무음이 없고 등록 순서가 정방향인 조건에서 MOSS는 Main 70발화 중 64개(91.4%)를 맞혔습니다. 이 원본 조건을 포함한 10가지 조건에서 모두 맞힌 발화는 47개(67.1%)였습니다. 8개 회의에서 추출한 구간 중 5개에서는 조건에 따라 예측 화자가 달라졌습니다.

이 챌린지에서 살펴보는 것

  1. 입력 변화에 대한 안정성: 앞 무음과 등록 순서를 바꾼 10가지 조건에서 화자를 계속 맞히는지 평가합니다.
  2. 실제 회의에서의 성능: AMI의 연속 대화 구간을 사용하고, 개발 데이터와 화자가 겹치지 않는 평가 세트를 따로 구성했습니다.
  3. 오류 유형: 등록 음성을 모델의 화자 ID에 잘못 연결한 경우와 대화 속 발화를 잘못 분류한 경우를 나누어 분석합니다.
  4. 어려운 발화에서의 한계: 겹치거나 짧은 발화에서는 모든 비교 방법의 불변 정답률이 65% 이하였습니다.

이번에 검토한 선행연구에서는 등록 음성을 사용하는 통합 모델의 화자 귀속을 이와 같은 입력 변화로 평가한 벤치마크를 찾지 못했습니다. 검토한 연구와 비교 내용은 아래에 정리했습니다.

03Task & Evaluation

과제와 평가 지표

등록 음성을 듣고, 회의 속 각 발화를 누가 말했는지 맞힙니다.

  • 입력: 연속 회의 음성 1개, 화자 2–4명의 등록 음성(각 3초짜리 2개), 평가할 발화의 시작·끝 시각입니다.
  • 출력: 각 발화를 등록된 화자 중 누구의 말로 판단했는지 화자 ID로 표시합니다.

예를 들어 A의 등록 음성을 들려준 뒤, 회의 속 발화가 그 사람의 말이면 A로 답하게 합니다. 예비 실험에서는 발화 구간을 제공해, 발화 경계를 찾는 과정과 구분해서 화자 연결을 비교합니다. 통합 모델의 출력 시각은 이 공통 발화 구간에 대응시켜 채점합니다.

아래 10조건과 발화 구간 제공 방식은 현재 예비 실험의 규격입니다. 향후 평가의 입력·출력과 ASR 채점 규격은 비공개 평가 환경을 검증한 뒤 별도로 안내합니다.

대화는 유지하고, 입력 조건만 바꿉니다

이번 통합 모델 구성은 등록 음성 뒤에 회의 음성을 이어 붙이고, 등록 구간에서 모델이 붙인 임시 화자 ID를 A–D와 연결합니다. 각 등록 음성 뒤에는 0.4초 간격을 둡니다.

평가에서는 회의 내용, 발화 순서, 등록에 쓰는 목소리를 유지하고 아래 두 요소만 바꿉니다. 사람과 목소리는 그대로이므로 발화별 정답도 같습니다. 모델이 입력의 위치나 나열 순서에 영향을 받는지 확인하기 위한 구성입니다.

  • 앞 무음 9가지: 입력 맨 앞에 0초부터 4초까지 0.5초 간격으로 무음을 넣습니다. 0초는 원본 조건이며, 나머지 조건에서는 뒤의 음성 전체가 같은 길이만큼 이동합니다.
  • 등록 역순 1가지: 앞 무음이 없는 상태에서 등록 음성의 나열 순서를 뒤집습니다. A–D의 사람을 다시 지정하는 것이 아니라, 같은 사람의 등록 음성을 놓는 순서만 바꿉니다.

원본을 포함해 총 10가지 조건입니다. 무음을 추가한 조건은 이동한 시각을 보정해 같은 발화끼리 비교하므로, 단순히 시간축이 밀린 것을 화자 오류로 세지 않습니다.

WeSpeaker는 원래 회의에서 잘라 낸 동일한 발화와 동일한 등록 목소리를 조건마다 비교합니다. 이번 구현에서는 조건별 예측이 같아, 한 조건에서 맞힌 발화만 모든 조건에서도 정답이 됩니다. 따라서 불변 정답률은 한 조건의 정답률과 같습니다. 실제 Hard 예비 실험에서는 예측 변경 수가 0이었지만, 모든 조건에서 맞힌 발화는 175개 중 113개(64.6%)였습니다. 나머지 62개는 같은 오답을 반복한 경우입니다. 즉, 입력 변화에 대한 안정성을 확보해도 짧거나 겹친 발화의 화자를 정확히 구분하는 문제는 남습니다.

무엇을 측정하나요?

각 발화를 고정된 등록 화자 ID와 비교해 맞거나 틀린 것으로 채점합니다. 같은 발화를 여러 조건에서 실행하더라도 평가 대상 발화 수는 늘리지 않습니다. 불변 정답률은 ‘모든 조건에서 맞힌 발화 수 ÷ 평가 발화 수’이며, 평균 정답률은 조건별 정답률을 평균 낸 값입니다.

발화의 길이와 겹침에 따라 두 트랙으로 나눕니다

짧은 발화는 목소리를 판단할 정보가 적고, 겹침 발화는 다른 사람의 목소리가 함께 섞입니다. 두 조건에서 얼마나 정확히 화자를 연결하는지 따로 확인하기 위해 트랙을 나눴습니다.

  • Main: 길이 0.8–15초, 다른 화자의 단어 구간과 겹치는 시간 비율이 5% 이하인 발화입니다.
  • Hard: 0.8–15초 발화의 가벼운 겹침(5% 초과 30% 이하)·심한 겹침(30% 초과), 0.3초 이상 0.8초 미만의 짧은 발화·짧고 겹친 발화로 나눕니다. 짧은 두 유형의 겹침 기준도 5%입니다. 클립 끝에서 잘린 발화는 제외합니다.

겹침 비율은 해당 발화 시간 중 다른 화자의 단어 시각과 겹치는 부분의 비율입니다. 단어 개수의 비율이 아닙니다. 유형은 주석의 길이·겹침 정보로 정하며, 특정 모델이 틀렸는지로 선정하지 않습니다.

04Dataset

평가 데이터 개편 예정

아래는 예비 실험에 사용한 AMI 데이터 구성입니다. Starter로 방법과 기준값을 정한 뒤, 다른 화자의 회의에서 잘 작동하는지 확인하려고 Held-out을 따로 구성했습니다. 방법을 정할 때 보지 않은 자료라는 뜻이며, 음성 파일이 비공개라는 뜻은 아닙니다.

Held-out은 8개 회의에서 추출한 연속 구간 8개이며, 회의 전체 녹음을 사용한 것은 아닙니다. 회의 음성 합계는 약 488초입니다. 이 자료는 이미 공개했으므로 새 비공개 평가셋과 분리하고, 여러 길이의 회의를 다루는 평가는 후속 데이터에서 검토합니다.

수정 방향

  • 공개 개발셋과 비공개 평가셋 분리: 개발셋은 참가자가 모델을 조정하고 실패 사례를 확인하는 데 사용합니다. 같은 평가 음성을 보며 반복 조정하는 영향을 줄이기 위해, 새 평가셋의 음성·등록 음성·정답은 운영자가 보관하는 방식을 준비합니다.
  • Hard 조건 중심으로 확장: 짧은 발화, 겹침 발화, 빠른 화자 전환을 우선 확보하고, 원거리 녹음과 생활 소음 등 다양한 상황을 추가로 검토합니다.
  • 길이별 평가: 회의 입력의 길이와 개별 발화의 길이를 따로 구분할 예정입니다. 긴 회의 안에도 짧은 맞장구가 있으므로, 두 길이를 나누어야 문맥 길이와 발화 정보 부족의 영향을 구별해 살펴볼 수 있습니다. 길이 구간과 표본 수는 데이터 확보 후 정합니다.
  • 평가 분리 기준: 같은 화자나 회의가 두 세트에 들어가면 그 특성에 맞춘 조정이 평가에 유리할 수 있으므로 중복을 확인할 예정입니다. 등록 음성도 채점할 발화 밖에서 골라, 같은 음성을 그대로 대조해서 맞히는 영향을 줄입니다.

데이터 출처, 구성 비율, 발화 구간 제공 방식은 검토 중입니다. 현재 공개된 음성을 새 비공개 평가 음성으로 취급하지 않습니다.

06Baselines & Method

비교 모델과 제안 방법

임베딩은 목소리의 특징을 숫자 벡터로 나타낸 값입니다. 코사인 유사도는 두 벡터의 방향이 얼마나 가까운지 나타내며, 여기서는 발화가 어느 등록 화자의 목소리와 더 비슷한지 비교하는 데 사용합니다.

MOSS가 출력한 ‘화자 1·화자 2’는 등록 인물 A–D와 다른 임시 ID입니다. 아래 방법들은 이 ID를 실제 등록 인물과 연결하는 방식이 다릅니다.

MOSS-Transcribe-Diarize 0.9B

전사, 발화 시각, 임시 화자 ID를 함께 출력합니다. A의 등록 음성이 놓인 시간에 ‘화자 1’이 출력되면, 대화 속 ‘화자 1’도 A로 연결합니다. 등록 구간에서 화자를 놓치거나 합치면 대화 구간의 연결도 잘못될 수 있습니다.

WeSpeaker ResNet34-LM

각 발화와 등록 음성의 임베딩을 비교해, 코사인 유사도가 가장 높은 화자를 고릅니다. 이번 구현은 같은 발화와 등록 음성을 비교하므로 조건별 예측이 유지됩니다. 짧거나 겹친 발화에서 목소리를 잘못 비교하면, 같은 오답도 반복할 수 있습니다.

제안: 임베딩 재연결·확인

MOSS가 같은 임시 ID로 묶은 대화 구간의 임베딩을 모아, 가장 비슷한 등록 화자와 다시 연결합니다. 이어 개별 발화의 유사도를 확인하고, 다른 화자의 점수가 현재 화자보다 0.10을 초과해 높을 때만 수정합니다. MOSS의 화자 예측이 없으면 임베딩으로 보완합니다. 전사와 발화 시각은 바꾸지 않습니다.

등록 구간의 ID 연결이 불완전할 때, 대화에서 실제로 들리는 목소리를 비교해 그 연결을 다시 확인하는 접근입니다. 다만 재연결과 발화별 보정이 각각 얼마나 기여했는지는 단계를 나눈 대조 실험으로 확인해야 합니다.

비교 조건을 유지하고 실행을 재현할 수 있도록 모델 버전(revision), 패키지 버전, 디코딩 설정(BF16, greedy), 입력·코드의 해시를 기록했습니다. 유사도 차이 0.10은 확률 10%를 뜻하지 않으며, Held-out 채점 전에 정한 수정 기준입니다.

07Findings

결과에서 확인한 점

01

대화가 같아도 화자 예측은 달라졌습니다.

Starter에서 확인한 입력 조건별 변화가 Held-out 8개 구간 중 5개에서도 나타났습니다. MOSS의 Main 70발화 중 23개는 적어도 두 조건에서 서로 다른 화자로 예측됐습니다. 이 수는 예측이 바뀐 발화 수이며, 모든 조건의 오답 건수를 합한 값과는 다릅니다. 동일 입력 재실행의 일치는 앞서 설명한 Starter 대조 실험에서 확인한 범위입니다.

02

무음이 길어질수록 더 틀리는 양상은 아니었습니다.

같은 발화가 앞 무음 1초에서는 맞고, 0.5초와 1.5초에서는 틀리기도 했습니다. 무음을 넣으면 발화가 음성 처리 단위인 30초 경계에 놓이는 위치도 바뀔 수 있어 이를 원인 후보로 검사했습니다. Starter 대화 2개의 대조 실험은 그 가설을 뒷받침하지 못했으며, 다른 근본 원인을 특정한 것은 아닙니다.

03

등록 화자 연결과 대화 속 분류에서 모두 오류가 났습니다.

Main 70발화를 10조건으로 평가한 700회 판단 중 오답이 129건이었습니다. 같은 발화라도 여러 조건에서 틀리면 각각 한 건으로 셉니다. 이 중 83건(64%)은 등록 화자 연결이 불완전한 상태에서 발생했고, 나머지 46건(36%)은 연결이 정상인 상태의 오배정 32건과 대상 출력 누락 14건이었습니다. 등록 연결 문제의 동반 여부로 나눈 분류이며, 앞의 83건이 모두 그 문제 하나만으로 발생했다고 단정하지 않습니다.

04

임베딩으로 다시 연결하자 Main 결과가 개선됐습니다.

등록 연결과 발화별 확인을 함께 적용하자 MOSS의 Main 불변 정답률은 67.1%에서 98.6%로 높아졌고, 예측 변경 수는 23개에서 0개로 줄었습니다. 이는 두 단계를 결합한 결과이며, 어느 한 단계의 효과만을 뜻하지 않습니다. WeSpeaker와의 차이도 작아 제안 방법이 더 우수하다고 판단할 근거는 아직 없습니다.

05

겹치거나 짧은 발화에서는 여전히 성능이 낮았습니다.

모든 비교 방법의 Hard 불변 정답률이 65% 이하였습니다. 특히 짧고 겹친 발화는 다음 단계에서 집중적으로 살펴볼 조건입니다.

결과를 해석할 때의 한계

  • 제안 방법이 WeSpeaker보다 우수하다는 근거는 아직 없습니다.
  • Held-out은 모두 4인 회의이므로, 화자 수에 따른 영향은 따로 확인하지 못했습니다.
  • 질문과 답변의 역할 전환이 오류의 직접 원인인지는 확인하지 못했습니다.
  • 겹침 구간에서는 주석의 발화 단위마다 말한 한 사람을 정답으로 삼았습니다. 같은 시간에 들리는 모든 사람을 한 번에 출력하는 과제와는 채점 단위가 다릅니다.
  • 현재 수치는 통합 모델의 출력에 등록 ID 연결과 공통 발화 구간 대응을 적용한 전체 과정의 결과입니다. 차이가 모델 내부의 특정 구조나 문맥 추론만으로 발생했다고 분리해 입증하지는 않았습니다.
08Evaluation & Submission

평가 방법과 제출 절차 개편 예정

음성 자체를 비공개로 두면 참가자가 평가 음성을 받아 예측 파일을 만들 수 없습니다. 따라서 실행 가능한 모델 패키지를 제출받고 운영자가 추론·채점하는 방식으로 전환할 예정입니다. 새 접수·평가 절차는 준비 중이며, 현재 공개 코드는 기존 예비 실험을 재현하는 용도입니다.

예정된 진행 방식

  1. 모델 실행 패키지 제출: 참가자가 실행 코드, 환경 설정, 모델 체크포인트 또는 고정된 다운로드 주소, 방법 설명을 준비합니다.
  2. 제출 버전 고정: 같은 제출 결과를 다시 확인할 수 있도록, 운영자가 실행 가능 여부를 검토한 뒤 평가에 사용할 코드와 모델 버전을 고정합니다.
  3. 운영자 환경에서 평가: 비공개 회의·등록 음성으로 조건별 추론을 실행하고, 공통 평가기로 화자 귀속과 전사 성능을 계산합니다.
  4. 집계 결과 공개: 운영자는 발화별 상세 결과로 채점을 검증하고, 참가자에게는 사전에 정한 집계 지표를 제공하는 방향입니다. 비공개 평가의 정답이나 개별 실패 항목을 반복 조정에 이용하는 영향을 줄이기 위해서입니다. 상세 실패 사례는 공개 개발셋에서 확인할 수 있도록 준비합니다.

제출 경로와 패키지 형식, 실행 자원·시간 제한, 제출 횟수, 공개할 집계 지표와 반영 일정은 평가 환경을 검증한 뒤 안내할 예정입니다. 상세 실패 사례는 공개 개발셋에서 제공하는 방향을 검토합니다.

기존 예비 실험 재현 방법 · 현재 공개 코드

아래 설명은 기존 공개 데이터와 10가지 입력 조건의 결과를 재현하기 위한 절차입니다. 새 비공개 평가의 제출 규격은 준비 후 별도로 안내합니다.

1. 조건별 입력 만들기

통합 모델용 입력을 생성합니다. 8개 구간을 10가지 조건으로 변형해 WAV 80개를 만듭니다. 전체 크기는 약 220MB입니다.

python speaker_project/make_condition_inputs.py --output condition_inputs   # 8구간 × 10조건 = 80개 WAV (약 220MB)

condition_inputs/condition_inputs.jsonl에는 이어 붙인 WAV에서 등록 음성이 놓인 구간과 이동 후의 발화 시각이 들어 있습니다. 모델 출력이 전체 WAV의 시각을 사용하므로 이 정보를 통해 원래 회의의 같은 발화와 대응시킵니다. 원본에서 각 발화를 잘라 처리하는 임베딩 방식은 원래의 inputs.jsonl을 사용해도 됩니다.

2. 조건별 예측 파일 준비하기

각 조건의 예측을 <조건>.jsonl 파일 하나에 저장하고, 총 10개 파일을 한 폴더에 넣습니다. 조건 이름은 pad0000ms_fwd, pad0500ms_fwd, …, pad4000ms_fwd, pad0000ms_rev입니다.

{"clip_id": "TS3010b_question_answer_reversal_01",
 "predictions": [{"segment_id": "segment_000", "speaker": "A"}, {"segment_id": "segment_001", "speaker": null}, …]}

화자는 등록 ID(A–D) 중 하나로 표시합니다. null이나 누락된 발화는 오답으로 처리합니다. Main과 Hard를 모두 채점할 수 있도록 입력에 포함된 모든 발화를 예측합니다.

3. 채점하기

python speaker_project/evaluate_submission.py --predictions my_predictions/ --output my_score.json

평가기는 Python 표준 라이브러리만 사용합니다. Main·Hard 불변 정답률, 평균·최저 정답률, 예측 변경 수, 동일 화자 발화 쌍, Hard 세부 조건별 점수를 출력합니다.

runs/speaker_heldout_01/submissions/의 비교 모델 예측 파일을 채점하면 위 리더보드의 수치를 재현할 수 있습니다.

비교 모델 실행과 데이터 재구성 방법
python speaker_project/download_wespeaker.py                     # WeSpeaker ONNX 모델 (약 26.5MB, SHA256 확인)
bash speaker_project/setup_moss_reuse_torch.sh                   # MOSS 전용 환경 (기존 CUDA PyTorch 공유)
python speaker_project/run_heldout_sweep.py --shard 0/1 --output runs/heldout   # MOSS 80회 (GPU, GPU 2장이면 0/2·1/2)
python speaker_project/analyze_heldout.py --run runs/heldout     # WeSpeaker·제안 방법 계산(CPU) + 제출 파일·점수 생성
  • MOSS 실행은 runs/speaker_moss_pilot_01/run_manifest.json에 기록된 모델 revision, 패키지 버전, 디코딩 설정을 사용합니다.
  • RTX A5000, PyTorch 2.4.0+cu118, Transformers 5.6.0, BF16, greedy 설정에서 MOSS 80회 추론은 합계 약 26분이 걸렸고, 최대 GPU 메모리는 약 2GB였습니다.
  • 정답은 모든 예측을 만든 뒤 채점할 때 읽습니다. 서버의 원본 출력은 runs/speaker_heldout_01/results_only.zip에 있습니다.
  • 기존 예비 실험 데이터는 저장소에 포함되어 있습니다. AMI 원본 주석으로 다시 구성하려면 download_ami.py, prepare_ami.py --scan-all, build_heldout.py 순서로 실행합니다.
